## 新服务器是否足够

足够开展单机模块化升级。当前 KVM 虚拟机获配 8 vCPU，宿主 CPU 型号 AMD EPYC 9645；不是独占 96 核。内存约 15.6 GiB，可用约 13 GiB；根盘约 503 GiB，可用约 474 GiB，采样时负载很低。未发现 `/dev/nvidia*` 设备，未配置 swap。

机器还运行其他应用、MySQL、面板和代理，不能把全部资源预算分给 BOT。该快照没有测量并发峰值、磁盘 IOPS、外部平台吞吐或模型服务容量，因此不能据此承诺能支持多少服务器或同时多少会话。

适合：独立媒体工作进程、全文检索、持久任务队列、更大且有配额的缓存、轻量 OCR/语音识别实验、管理面板。大型语言模型/高质量绘图仍优先调用外部服务；8 vCPU 和 16 GB 内存不等于适合部署高质量大模型。

## 先处理的具体问题

1. **系统管理开发者判定失效。** `system_admin.py:76` 的 `_read_owner_discord_id()` 只在环境变量为空时返回默认值，配置了 ID 时直接返回 `None`；原来的转换代码落到了下一个函数已经 return 的后面。用虚构配置 ID 的独立 AST 探针已复现 `None`，不需要真实凭据。`SystemAdmin` 依赖该返回值判断开发者，因此配置了 ID 时，其开发者专用操作会被拒绝。这里只确认并记录，未顺手修改线上代码。
2. **代码职责集中。** `chat/cog.py` 6937 行，`chat/agent/discord_tools.py` 2620 行，`music/cog.py` 2227 行。聊天入口同时承担视觉/PDF、会话恢复、任务展示、工具协调及限流，增加功能很容易影响原功能。
3. **跨环境与多服务器配置不统一。** 当前服务端存在写死的开发者、服务器、身份组、频道和表情 ID，部分原环境变量配置被替换。可保留现网行为作为迁移默认值，但通用多服务器配置应进入统一配置层并保留宿主权限校验。
4. **部署基线与测试覆盖需补齐。** Python 安装脚本未完整锁定版本；Node 虽已锁版本，但依赖 DSH rc.6 的受校验补丁。根 README 仍提到已移除模块。升级运行时前应有离线恢复、权限、取消和重试回归，以及依赖清单与可回滚发布包。

## 推荐改造顺序

### 第一阶段：稳定核心与可回滚发布

- 修复已确认的开发者 ID 读取，补上正数/空值/非法值测试；恢复关键历史回归用例。
- 保留当前行为，把聊天接入、会话/记忆、工具执行、附件理解、回复展示逐步拆分。先抽接口，再替换实现，不一次性推倒重写。
- 为每次互动和工具调用增加关联 ID，记录真实工具调用、耗时、错误类别、重试次数和压缩前后用量。沿用脱敏，不把聊天正文和凭据放进常规日志。
- 固定依赖和迁移步骤；代码发布与会话、数据库、凭证分开管理。先在独立测试 Bot/服务器验证，再逐步启用，生产始终只运行一个 Discord Gateway 实例。

### 第二阶段：可恢复任务与重任务隔离

- DSH 已经是按服务器分开的 Node 子进程，FFmpeg/yt-dlp 也已有子进程与超时；应在现有隔离上补持久任务状态和资源预算，不是把所有东西重新“改为异步”。
- 将媒体下载/转码、PDF/OCR 等重任务交给有限数量的工作进程。起步控制为少量 CPU 重任务并行，实时点歌优先于预取；分别限制 CPU、下载、每上游 API 和每服务器请求量。
- 使用 SQLite WAL 等简单存储持久化待执行/执行中/成功/失败/取消状态。重启后可以恢复安全的读任务；写 Discord 的角色创建/处罚任务先核对实际结果，不能自动重放造成重复处罚或重复建组。
- 工具定义由统一注册表生成 Python 校验与 JS schema，工具版本进入会话能力刷新逻辑；当前服务器、真实请求者权限、字符串雪花 ID 仍由宿主绑定，不交给模型猜。

### 第三阶段：真正可查的长期记忆

- 保留近期原文＋带覆盖范围的摘要；更老消息进入分服务器、分频道的检索存储，先做全文检索，再按实测考虑向量检索。
- 检索结果按当次权限过滤，并携带消息 ID、时间、原链接与来源；私密频道不能因检索而泄漏给其他频道。
- 把临时表情索引、成员目录、工具能力和本轮权限放在临时上下文，不反复写进永久聊天历史。实体解析优先 ID，昵称仅用作搜索并处理歧义。
- 对“今天比赛结果/歌词”等问题展示实际搜索工具状态；上游未提供检索证据时标记未核实，不能只靠提示词让模型声称已联网。

### 第四阶段：用户能明显感受到的功能

- 多平台音乐适配层：QQ/网易云等保持统一队列和 Agent 点歌接口，明确来源与是否能取得官方可播放音频，不承诺免会员播放付费歌曲。
- PDF/网页资料库：异步导入、按页检索、回答附原页码，长文档不直接全部塞进聊天上下文。
- 统一管理面板：按服务器看能力、权限、队列、模型、凭证健康和故障原因；敏感配置仅开发者可改，服务器服主/admin 仅管理其服务器获授权部分。
- 可选语音收发：先外部 ASR/TTS 或轻量 CPU 方案做延迟测试；必须有明确频道开关、知情提示和录音保留策略，再考虑常驻语音助手。

## 结论

可以大改造，建议路线是“稳定核心 → 任务隔离 → 检索记忆 → 新功能”。新主机主要改善资源余量、并行处理和存储，不会自动修复模型幻觉、外部平台风控、上游 API 失败或权限逻辑错误。首批落地应是核心可靠性与可观测性，再用真实延迟、成功率、内存峰值和每轮 token 指标决定下一步扩容。
